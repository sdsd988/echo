# echo 프롬프트 가이드 — 4-2 도구 계층

> **진입:** `git checkout v4.2-baseline` (4-1 결과인 CLAUDE.md·rules가 이미 깔린 상태)
> 아래 프롬프트를 **순서대로** Claude Code에 붙여넣으세요. 결과로 글 **조회** API(`GET /posts`, `GET /posts/{id}`)가 생깁니다.
> 이번 절의 주제는 "코드를 새로 짜내는" 게 아니라 **Claude가 자기 손(Built-in Tools)으로 기존 코드를 읽고 → 그 패턴 그대로 확장**하는 걸 보는 겁니다. 작성(`POST /posts`)은 seed에 이미 있어요.

## S1 — Built-in Tools로 기존 패턴 읽기

확장하기 전에 먼저 *읽힙니다*. Claude가 Grep·Read로 코드베이스를 훑어 작성 흐름과 컨벤션을 스스로 파악하게 합니다. (우리가 파일을 일일이 안 붙여넣어도 됨)

```
post 글 작성이 지금 어떻게 구현돼 있는지 코드를 읽고 설명해줘.
Controller → Service → Repository로 이어지는 흐름과, 이 프로젝트가 지키는
컨벤션(ApiResponse 래핑, DTO record, 계층별 책임, 도메인 모듈의 Spring Web 의존 금지)을
짚어줘. 아직 코드는 바꾸지 마.
```

---

## S2 — 읽은 패턴 그대로 조회로 확장

이제 방금 파악한 패턴을 *그대로 따라* 조회를 추가합니다. 새 발명이 아니라 **모방**입니다. `.claude/rules`가 깔려 있어 계층 규칙(서비스는 POJO라 HTTP 404를 못 던짐 → 컨트롤러 책임)을 Claude가 알아서 지킵니다.

```
방금 읽은 POST 패턴을 그대로 따라서 글 조회 기능을 추가해줘.
- GET /posts/{id} : 단건 조회. 없는 글이면 404
- GET /posts : 최신 글부터 정렬한 목록 조회
규칙: .claude/rules의 계층 규칙을 지켜. 도메인/application 모듈은 Spring Web에 의존하면 안 되니까
조회 결과가 없을 때의 404 같은 HTTP 처리는 apps/customer-api(컨트롤러)에서 해.
응답은 기존처럼 ApiResponse로 감싸고, DTO는 record 그대로 재사용해.
```

## S3 — Built-in Tools로 빌드·테스트 검증 + 테스트 보강

Claude가 자기 손으로 빌드를 돌려 초록인지 확인하고, 조회 엔드포인트의 통합 테스트까지 추가합니다.

```
빌드하고 테스트를 돌려서 다 통과하는지 확인해줘(./gradlew build).
그리고 방금 추가한 GET /posts, GET /posts/{id}에 대한 통합 테스트도 기존 PostIntegrationTest 스타일로 추가해줘 —
글을 만든 뒤 단건·목록이 조회되는지, 없는 id는 404인지.
```

## 끝난 뒤 확인

- `PostController`에 `@GetMapping` 두 개 (목록·단건) 추가됨
- `PostService`에 `findById`(Optional 반환)·`findRecent` 추가 — 클래스 레벨 `@Transactional(readOnly=true)` 그대로
- `PostRepository`에 `findAllByOrderByCreatedAtDesc()` 추가
- `./gradlew build` 통과, GET 통합 테스트 초록
- Swagger UI에 `GET /posts`·`GET /posts/{id}` 노출

> 다 끝내면 이 상태가 `v4.3-baseline`입니다. 막히면 `git checkout v4.3-baseline`으로 정답과 비교하세요.
